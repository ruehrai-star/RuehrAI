# @ruehrai/api-contracts

OpenAPI **v0.19.3** für die RuehrAI-API. Das ist der Vertrag, den Clients konsumieren. `0.2.0` ergänzt Logout, Zielregion, Filialadressen und Monatsumsatz. `0.3.0` ergänzt die Musteranalyse (`/analysis/input`, `/analysis/runs`, `/analysis/pattern`). `0.4.0` ergänzt Top-3-Empfehlungen (`POST /recommendations`, `GET /recommendations`) mit Titel, Ort, Score und deutscher Begründung. `0.5.0` ergänzt Kartenpins und die Zielregion: Filialen liefern WGS84 `lon`/`lat` (PLZ-Schwerpunkt, wenn der Write beide weglässt), die Zielregion liefert `bounds` (west, south, east, north) für `fitBounds` und `geometry` (GeoJSON Polygon/MultiPolygon) für die farbige Fläche. `0.6.0` ersetzt die einzelne Zielregion durch eine Liste: `GET /target-region` liefert `items`, `POST /target-region` hängt einen Katalogort an, `DELETE /target-region/{geoKey}` nimmt einen Ort heraus, `DELETE /target-region` leert die Liste. Es gibt kein `PUT`, das die einzige Zeile überschreibt. `0.6.1` ergänzt `gemeinde` in `CatalogLevel` für eine Gemeinde (grain `ags`). `0.7.0` ergänzt `POST /address-pair`: zwei Adressen, Lookup nur über die PLZ, Themen auf Gemeinde / Kreis / Land. `0.8.0` ergänzt `AnalysisPattern.yearlySeries`: Dreijahresreihe der kleinräumigen Brain-Kennzahlen für die Zielregionen. `coverage: single` ist kein Trend. `0.9.0` mappt die weiteren Brain-Mehrjahres-Themen (einschließlich `ba_sgb2`), bevorzugt lokales Unfallatlas Gebiet, verankert das Jahresfenster an verfügbaren Brain-Perioden und berechnet `yearlySeries` bei GET neu. Platzhalter-Nullen (KBA Elektro) und Geo-Schlüssel (`ba_schluessel`) sind keine Series-Werte. Zählwerte (Wohnungen, Einwohner, Altersbänder, SGB2) sind ganze Zahlen; Anteile bleiben gebrochen. Ein Ortsteil-Ziel gibt die `yearlySeries`-Liste weiter (Gemeinde-/Kreis-/Land-Fallback). Grain `ags5` / ein 5-stelliger AGS ist `kreis` in `requestedLevel` (`SeriesLevel`), nicht `gemeinde`. `0.10.0` lässt `GET /analysis/pattern` optional `geoKey` zu. `0.11.0` stellt Musteranalyse-Kriterien auf die Filialumgebung und `POST /recommendations` auf Teilflächen in der Zielregion mit Dreijahres-Trend und Stichtag-Label um. `0.12.0` liefert nur die feinste Ebene je Zielregion (Adresse → Raster → Ortsteil → PLZ5 → Bezirk → Gemeinde) und kennzeichnet übernommene Kriterien als `scope: inherited`. `0.12.1` mappt kleinräumige Jahresreihen auf die Ebene des Treffers: `hamburg_stadtteil_regionalstatistik` → Ortsteil, `muenchen_indikatorenatlas` → Stadtbezirk, `berlin_lor_ewr_bevoelkerung` → LOR. `0.13.0` korrigiert die Reihenfolge Adresse → Raster → LOR-Planungsraum / Köln-Quartier (`quartier`, `koeln:sq:*`) → Ortsteil → PLZ5 → Bezirk → Gemeinde; Berlin 2021 PLR (`lor:plr:*`) und 2006 LOR bleiben getrennte Reihen; Adressen kommen aus `geo.geo_ref_address` (leer = überspringen); weitere Themes Köln/Leipzig/Düsseldorf/Essen/Frankfurt. Lokale Reihen vor inherited; fehlende Jahre bleiben absent. `0.14.0` baut das Filial-Muster spiegelbildlich auf jeder Ebene und exposiert `RecommendationSet.patternByLevel` (Musterprofil je Ebene, Kreis nur `role: frame`). `0.15.0` vergleicht **Datensätze** (nicht Ebenen): Rohwerte werden auf die Fläche baselined (`per_1000_inhabitants` | `per_km2` | `per_household`); der Dreijahrestrend läuft auf `normalizedValue`; fehlende Bezugsgröße ist `absent` (nie 0). `patternByDataset` ist das Vergleichsprofil; `PatternCriterion` / `RecommendationEvidence` weisen `metricId`, `baseline`, `rawValue`, `normalizedValue` und Flächenebene (`sourceLevel`) aus. Berlin-Bezirk vs Köln-PLZ matchen relativ. `0.16.0` liest Bezugsgrößen aus Brain `geo.area_baseline` + `geo.baseline_metric_catalog` und stellt `baselineMethod` (`official` | `estimate_lor_sum` | `estimate_address` | `missing` | `geom` | `fixed_grid`) auf Punkte, Kriterien und Evidence; `missing` lässt `normalizedValue` weg und teilt nie durch 1. `0.17.0` ergänzt `official_zensus2022_grid` und `estimate_zensus2022_grid_sum` (Zensus-2022 100m-Gitter; Address nur Fallback). `0.18.0` ergänzt Treffer-`geometry`, `trend` und `baselineMatch`. `0.18.1` speichert das Recommendation-Set mit `POST /analysis/runs` und lässt `GET /recommendations` optional `runId` zu (nur lesen, nie berechnen). `0.19.0` ergänzt offizielle Top-Level-Felder `grain` / `name` / `parentLabel` auf `Recommendation`, `intersectionOf` für Schnittflächen-Teile und den Laufstatus `queued` | `running` | `completed` | `failed` auf `AnalysisRun` (completed erst nach persistiertem Set; failed wenn Pattern oder Set-Berechnung scheitert). `0.19.1` füllt `Recommendation.name` immer (Fallbacks `PLZ 80331` / `Planungsraum ohne Namen` / `Quartier ohne Namen` / `{Art} ohne Namen` / `100-m-Rasterzelle`, nie Keys, IDs, LOR-Nummern oder `Quartier <id>`), setzt `parentLabel` auf die Gemeinde unterhalb der Gemeinde-Ebene und ergänzt optionales `overlaps` (Anteile auf der an der Zielregion beschnittenen Trefferfläche; Punkte `ST_Covers` / share 1). `0.19.2` vergibt `rank` je `targetRegionGeoKey` (1-basiert, lückenlos, alle Ebenen gemeinsam nach score; Fallback `geoKey` → `ags:{ags}` → `label:{normalisiertes Label}`, listed in additive `RecommendationSet.targetRegions`); dieselbe Fläche in zwei Zielregionen ist zwei Items (`id` mit `@{targetRegionGeoKey}`), `dataAsOf` ist der jüngste Evidence-Zeitpunkt, der Musterverlauf bleibt auf `patternByDataset`. Quote: n≤66 ≥3 Plätze, 67–200 ≥1 (`floor(200/n)`); >200 Zielregionen → 400 auf `POST /analysis/runs` (kein stilles Weglassen; `POST /target-region` hat kein Nutzer-Limit). `0.19.3` nimmt optional `markedTargetRegionGeoKey` auf `POST /analysis/runs` an (Web-Alias `{ geoKey }` / `?geoKey=`), liest gespeicherte `yearlySeries` auf GET, und schneidet Berlin-LOR / Adresse / Raster / Quartier für Ortsteil-Zielregionen über `ST_Intersects` / `geo_ref_zielregion_teil` statt Gemeinde-AGS `11000000`. Additive; keine DB-Migration. `POST /auth/login` und `POST /auth/register` bleiben in Request und Response unverändert.

Basis-URL ist umgebungsabhängig. Lokal steht im Dokument `http://localhost:3000` (Backend-`PORT`, Default 3000).

```bash
pnpm --filter @ruehrai/api-contracts test
pnpm --filter @ruehrai/api-contracts build
```

`src/generated.ts` und `openapi/openapi.json` werden aus dem YAML erzeugt. Änderungen am Vertrag gehören ins YAML, danach `pnpm generate`.
